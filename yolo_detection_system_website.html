1. Open this page on your phone's browser (Chrome recommended)
2. Tap Start Camera — allow the permission popup
3. Use Flip Cam to switch between front and rear cameras
4. On desktop: plug in your phone as a webcam via USB (requires DroidCam or EpocCam app)
5. For GSM verification: when motion is detected, your SIM800L module sends an SMS OTP — enter it on the lock screen

Note: Camera access requires HTTPS. If running locally, use ngrok to tunnel or run via localhost which browsers whitelist automatically.

// System architecture

How the detection
system works

YOLO (You Only Look Once) processes the entire image in a single forward pass through a convolutional neural network, making it dramatically faster than older two-stage detectors like R-CNN.

01 — 📡

Frame capture

The mobile camera streams frames via WebRTC or USB. Each frame is captured at configurable intervals and passed to the YOLO inference pipeline.

02 — 🔲

Grid division

Each frame is divided into an S×S grid. Every grid cell predicts B bounding boxes with confidence scores and C class probabilities simultaneously.

03 — 🧠

CNN inference

The image passes through deep convolutional layers (darknet backbone or CSPNet in v5/v8). Features are extracted at multiple scales for small and large object detection.

04 — 📦

NMS filtering

Non-Maximum Suppression removes duplicate bounding boxes. Only the highest-confidence prediction per object survives, reducing noise dramatically.

05 — ⚡

Alert trigger

When a target class (person, vehicle, etc.) is detected above a confidence threshold, the system triggers an alert — sending an SMS OTP via the GSM module.

06 — 🔐

GSM verification

The SIM800L GSM module sends a one-time password via AT commands over UART serial. The operator verifies identity before remote access or alarm is granted.

// Hardware & software stack

Components used

This system combines embedded hardware, computer vision, and cellular communication into a single integrated detection pipeline.

Core compute
Raspberry Pi 4 / ESP32-CAM
Runs the YOLO model locally or streams to a server. Raspberry Pi handles full YOLOv8 inference. ESP32-CAM is used for lightweight streaming only.
Detection model
YOLOv8 (Ultralytics)
State-of-the-art single-stage object detector. Runs on CPU or GPU. Supports 80+ COCO classes. Custom training available with labeled datasets.
Camera module
Mobile phone / Pi Camera
Mobile browser camera via WebRTC, or a dedicated Raspberry Pi Camera Module v2 for fixed installations. Supports 1080p at 30fps.
GSM module
SIM800L / SIM900A
Communicates via UART serial using AT commands. Sends SMS alerts and OTP for secondary verification. Requires a SIM card with SMS enabled.
Prototyping
Breadboard + Jumper wires
Full-size solderless breadboard for circuit prototyping. Multi-color jumper wires for UART, power, and GPIO connections between modules.
Power
5V USB / LiPo Battery
System powered via USB-C (Raspberry Pi) or a 3.7V LiPo with booster for ESP32 deployments. SIM800L requires stable 4.2V — use a separate regulator.
Software stack
Python + OpenCV + Flask
Python drives inference via Ultralytics API. OpenCV handles frame capture and drawing. Flask serves the web dashboard and video stream endpoint.
Visual indicators
LEDs (Red + Green)
Red LED signals detection alert or armed state. Green LED indicates system ready or safe state. Driven via GPIO pins with 220Ω current limiting resistors.

// Limitations & trade-offs

Known limitations

No system is perfect. Here are the documented constraints and trade-offs of this YOLO-based GSM detection setup that you should be aware of before deployment.

01

High compute demand

YOLOv8 requires significant CPU/GPU resources. On a Raspberry Pi 4, inference runs at 3–8 fps — inadequate for high-speed scenarios. A GPU or NPU is needed for real-time 30fps performance.

02

GSM latency

SMS delivery via SIM800L is not instantaneous. Network congestion or poor signal can delay OTP delivery by 10–60 seconds, creating a gap in the verification window.

03

False positives

YOLO can misclassify objects in low light, partial occlusion, or unusual angles. Without fine-tuning on your specific environment, false alarm rates can be high.

04

Camera dependency

The system is only as good as the camera placement and quality. Motion blur, lens distortion, and infrared limitations at night degrade detection accuracy significantly.

05

No encryption on serial

UART communication between microcontroller and GSM module is unencrypted. Physical access to the breadboard allows interception of AT commands including OTP strings.

06

SIM800L power instability

The SIM800L draws up to 2A in bursts during transmission. Powering it from the same rail as the Pi causes voltage dips and crashes. Requires a dedicated power supply.

07

Limited class coverage

Default YOLO weights cover 80 COCO classes. Detecting domain-specific objects (weapons, specific vehicles, industrial equipment) requires custom dataset collection and retraining.

08

No persistent logging

In the current setup, detection events are not stored to a database. A power cycle loses all event history. Requires integration with SQLite or a cloud logging endpoint.
